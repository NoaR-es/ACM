# US-20.05 — Autenticar cada conexión MCP · Refinamiento

Sprint: SPRINT-004

Origen B:US-16.02 sin criterios: se definen aquí.

## Criterios de aceptación
- CA-01: Una petición MCP por HTTP sin token válido recibe 401 y no ejecuta nada.
- CA-02: Un token desconocido se rechaza y el intento queda registrado sin guardar el token completo.
- CA-03: Cada petición se atiende con la identidad de su propio token, también con varios agentes a la vez.

## Precondiciones
- ACM servido por HTTP (`acm serve`).

## Flujo
1. Cada petición HTTP a `/mcp` pasa por `BearerAuth`, que exige `Authorization: Bearer acm_…`.
2. El token se valida contra la base en cada petición (no hay sesión, ADR-014); la identidad queda en el contexto de la petición.
3. Una petición sin credencial válida recibe 401 con `WWW-Authenticate: Bearer realm="acm"`, no llega al servidor MCP y queda auditada como `http:auth`, solo con el prefijo del token.

## Alternativas
- Modo stdio (`acm mcp-stdio`): no hay red; el principal es `ACM_PRINCIPAL`, el del usuario del sistema que lanza el proceso (ADR-017).
- `/api/health` es público.

## Errores
- Sin cabecera, esquema distinto de Bearer o token que no es de ACM → 401.
- Token desconocido o revocado → 401.

## Reglas
- La identidad nunca sale de la configuración en HTTP.
- Verificado: la identidad de la petición llega a la herramienta sin mezclarse entre peticiones concurrentes.

## Casos límite
- Un token revocado a mitad de una conexión deja de valer en su siguiente petición.
