# US-18.03 — Gestionar migraciones · Refinamiento

Sprint: SPRINT-001

## Precondiciones
- La base (global o de proyecto) existe o puede crearse.

## Flujo
1. Al abrir una base, el migrador crea si falta la tabla `schema_migrations(version INTEGER PRIMARY KEY, name TEXT, applied_at TEXT)`.
2. Obtiene las migraciones del conjunto correspondiente (`global` o `project`), ordenadas por versión.
3. Para cada versión pendiente, en orden: `BEGIN IMMEDIATE` → ejecuta sus sentencias una a una → inserta la fila en `schema_migrations` → `COMMIT`.
4. La versión actual (máxima aplicada) se puede consultar con `acm_system_info` (global) y `acm_project_open` (proyecto).

## Alternativas
- Base ya al día: no se ejecuta nada.

## Errores
- Fallo de una sentencia → `ROLLBACK` de esa migración (incluido su registro) y error `MigrationError` con la versión y la sentencia. Las migraciones anteriores ya confirmadas se mantienen.
- La base tiene una versión mayor que la última conocida por el código (base de una versión futura de ACM) → error y no se abre.

## Reglas
- Cada migración tiene versión entera única y nombre; las versiones son consecutivas desde 1.
- Las migraciones se definen como listas de sentencias SQL (no `executescript`), para que la transacción las envuelva.
- Una migración publicada no se modifica: los cambios son migraciones nuevas.

## Validaciones
- Al cargar el catálogo se comprueba que las versiones son únicas, consecutivas y empiezan en 1.

## Casos límite
- Dos procesos abriendo a la vez una base sin migrar: `BEGIN IMMEDIATE` los serializa. El segundo vuelve a comprobar las versiones pendientes dentro de la transacción y no aplica dos veces la misma.
- Migración que falla en su segunda sentencia: la primera tampoco persiste.
