# US-13.05 — Detectar inconsistencias de SQLite · Refinamiento

Sprint: SPRINT-005

Origen B:US-01.08 sin criterios: se definen aquí.

## Criterios de aceptación
- CA-01: Se detectan la corrupción física de la base y las relaciones rotas (claves foráneas).
- CA-02: Mientras exista la inconsistencia, ACM no opera sobre ese estado: rechaza las escrituras del proyecto.
- CA-03: Una vez reparada, una nueva auditoría lo detecta y vuelve a permitir las escrituras.

## Precondiciones
- Proyecto accesible.

## Flujo
1. El Watchdog ejecuta `PRAGMA integrity_check(20)` y `PRAGMA foreign_key_check` sobre la base del proyecto.
2. Cada problema es un hallazgo CRITICAL: `SQLITE_INTEGRITY`, `SQLITE_FOREIGN_KEY` (con tabla y fila) o `DB_UNREADABLE` si la base no se puede leer.
3. Si hay alguno, el proyecto pasa a `integrity_status = 'corrupt'` (cuarentena, US-13.11) y no se evalúa nada más sobre esa base.
4. Una auditoría posterior que la encuentre sana la devuelve a `ok`.

## Errores
- Base ilegible → `DB_UNREADABLE`, sin excepción hacia el llamante.

## Reglas
- El estado de integridad vive en la base global (sobrevive a una base de proyecto dañada).
- El esquema no tiene triggers: la parte de "triggers" del enunciado no aplica todavía.
